# Gotchas

Project-specific facts that are easy to miss. Not a diary, not general advice.

## Vercel installs from a frozen pnpm lockfile
**Problem:** `package-lock.json` looks like the source of truth.
**Reality:** Vercel runs `pnpm install --frozen-lockfile`. A dependency change that doesn't update `pnpm-lock.yaml` fails the deploy. `pnpm-workspace.yaml` sets `allowBuilds` (sharp true, msw false, unrs-resolver false).
**Rule:** Update both lockfiles (`pnpm install --lockfile-only`, `npm install --package-lock-only`) and verify with a clean `pnpm install --frozen-lockfile` + `next build`.

## `next build` does not fail on type errors
**Problem:** A green build looks like clean types.
**Reality:** `next.config.mjs` sets `typescript.ignoreBuildErrors: true`.
**Rule:** Run `npx tsc --noEmit -p .` yourself.

## One place for the backend URL
**Reality:** `lib/api.ts` `API_BASE` defaults to `https://sentria-8btn.onrender.com`; `NEXT_PUBLIC_API_URL` overrides it. A stale value on Vercel points the app at the wrong API. `apiFetch` adds the Supabase token to every call.
**Rule:** Never hardcode a backend URL elsewhere; call `apiFetch`.

## Several API routes return 200 on failure
**Problem:** `res.ok` means success.
**Reality:** `/alerts`, `/recommendations`, contractors and assignments answer 200 with `error_code`. `lib/crm.ts` wraps them in `{ok, data}` / `{ok:false, code, detail}`.
**Rule:** Go through those wrappers; never trust `res.ok` alone for those routes. `/ask`, `/upload`, `/admin`, `/alerts/feedback` use real error statuses (the Ask screen reads `detail.message`).

## Use theme tokens, not `dark:` classes
**Reality:** `dark:` doesn't follow the "system" theme (`@custom-variant dark` is `.dark *`; under "system" there is no `.dark` class, only the `prefers-color-scheme` token overrides). The pricing check marks were dark green on a dark card for that reason. Colours live in `app/globals.css` (`--canvas`, `--ink`, `--tag-*`).
**Rule:** Use tokens. Keep the pastel tag tokens; changing them has been rejected twice. A surface that stays bright in dark mode (pricing's lime and green cards) takes `.tags-light`, which pins the light tag colours inside it. A dark surface does not: the sidebar's plan tag (`StatusTag`, one tone and icon per plan) uses the theme's tokens, and `tests/e2e/screens.js` fails any bright pastel tag in dark mode. `tests/e2e/brand.js` fails on a `dark:` class in the main views.

## Icons are generated
**Reality:** `lib/icons.tsx` and `lib/icon-data.ts` are generated.
**Rule:** Edit `scripts/icon-map.mjs`, run `node scripts/build-icons.mjs`; never hand-edit the outputs.

## dashboard-view.tsx early returns
**Problem:** Industry/Logistics overviews look like separate pages.
**Reality:** They are early returns inside `dashboard-view.tsx`. Each must keep `{importPortal}`, and `{sheetTabs}` as the **last child** (the bar is sticky). `tabSector`, `departmentTabs`, `activeDepartment`, `sheetTabs` are computed before those returns.
**Rule:** Moving or adding a return path means re-adding both.

## Settings follow the account only if listed
**Reality:** `lib/account.ts` `ACCOUNT_KEYS` are synced to `accounts.profile` (polled every 2 s). Other `sentria_*` localStorage keys stay in the browser.
**A view that saves an account value calls `requestAccountSave()` (`lib/account.ts`).** It saves at once and marks `sentria_account_dirty` until the server has it. Without it, the value waits for the next 2 second look, and a reload in that gap loaded the saved account over it: the wholesalers list vanished that way. While the mark is set, a page load keeps this browser's values and sends them. The mark is also why the first look after a load sends everything when it is set.
**Rule:** New setting that must follow the user: add its key there, and call `requestAccountSave()` after writing it. `tests/e2e/accountsync.js` guards this.

## Plan and admin flags in localStorage are UI-only
**Reality:** `sentria_plan`, `sentria_trial_ends_at`, `sentria_is_admin` only drive the UI. The server enforces plan on `/upload`, admin on `/admin`, `/ask` limits. Site limits (`maxSitesFor`) are currently UI-only.
**Rule:** Never treat a client check as security.

## Task keys and statuses
**Reality:** A task is keyed `${equipment}-${alert_key}` (`taskKeyFor`); repeat alerts are one task. `asStatus()` in the board maps unknown statuses to `todo`, so `dismissed` is handled separately (dismissed cards are filtered out and listed under "Dismissed").
**Rule:** Add any new status to the board's handling explicitly, and to `AssignmentStatus` in `lib/crm.ts`.

## Value tags: `currency` marks money
**Reality:** `valueAtRisk()` reads `value` only when `currency` is present; a bare `value` is a percentage (retail shrinkage). `basis: "sales"` marks an estimate (shown with ≈).
**Rule:** Don't show a bare `value` as money.

## Hover-only controls break touch and Playwright
**Reality:** A `pointer-events-none` / hover-only button can't be clicked by Playwright or on a phone.
**Rule:** Keep the board's ⋯ detail button always visible.

## `--sidebar` is not just the sidebar
**Problem:** The sidebar's colour looks like `--sidebar` alone.
**Reality:** `bg-sidebar` also paints dark hero cards in `dashboard-view.tsx` and `logistics-ui.tsx`. The sidebar's own surface is `--sidebar-shell` (black in light mode, `--brand-deep` green in dark, explicit or system). `--brand-deep` (#0f2e1f) is a palette colour, the same in every theme: pricing's Entreprise card, the billing toggle and AI panel, and the sign-in screen's sector panel all use `bg-brand-deep`. The green sidebar was reverted once after a report that it was invisible, then restored at the founder's request. The cause of the report was never identified (it was not reproduced, and the green measured more distinct from the page than the old black).
**Rule:** To recolour the sidebar, change `--sidebar-shell`, never `--sidebar`. Use `bg-brand-deep` / the tokens, never the hex.
**Deep-green surfaces in dark mode (light mode keeps its normal colours):** `bg-sidebar-shell` (the sidebar, and the "What needs your attention" banners in `dashboard-view.tsx` and `logistics-ui.tsx`), `bg-deep-card` (the "Your priorities" tiles and pills in `priority-nav.tsx`), `bg-deep-bar` (the pinned department tab bar in `sheet-tabs.tsx`). The other `bg-sidebar` dark cards stay black.

## A dialog owned by the sidebar must sit beside the `<aside>`, not in it
**Problem:** A `fixed inset-0` overlay rendered inside `sidebar.tsx`'s `<aside>` looks right in the code.
**Reality:** The `<aside>` has a transform (`translate-x-0`, `lg:translate-x-0`), which makes it the containing block of its `fixed` children: the overlay would cover the sidebar only, not the screen.
**Rule:** Render sidebar dialogs as siblings of the `<aside>` (in the component's fragment), with `z-[60]` to clear its `z-50`. The sign-out confirm does this.

## Alert thresholds on the Admin page come from the API
**Reality:** `components/sentria/admin-thresholds.tsx` renders whatever `GET /admin/thresholds` returns: names, groups, labels (fr/en), units, ranges and defaults all live in the backend's `pipeline/thresholds.py`. Saving sends `{value}` (a number) or `{value: null}` to put the default back. Overrides are global and apply from the next upload. Before the backend's migration 011 the API says `persisted: false` and the page disables editing.
**Rule:** Never list a threshold, label or range in the frontend. A new tunable number is a backend registry entry; this page shows it with no change here.

## Running the browser tests
**Reality:** Build from a clean copy (`pnpm install --frozen-lockfile` + `next build` with `NEXT_PUBLIC_SUPABASE_URL=https://sentria-test.supabase.co NEXT_PUBLIC_SUPABASE_ANON_KEY=test-anon`), `next start -p 3201`, then `node tests/e2e/<suite>.js`. `tests/e2e/auth-mock.js` fakes Supabase. `ss` isn't installed and `pkill -f "next start"` kills your own shell: free the port with `fuser -k 3201/tcp`, and always do it before a rebuild or you test a stale server. On a phone-width viewport open the menu before clicking sidebar items. `run-all.js` takes 10+ minutes.

## Motion comes from transitions.dev, in `app/transitions.css`
**Problem:** Menus, dialogs, KPI numbers and the attention banner animate, but there is no animation library and the `transitions-*` skill folder is not in the repo.
**Reality:** `app/transitions.css` holds four snippets of transitions.dev's free transitions (menu dropdown, modal, number pop-in, texts reveal), pasted verbatim with their reduced-motion blocks; its licence lets the app ship them but forbids redistributing the library. The `.is-open` / `.is-closing` / `.is-shown` classes are driven by `lib/use-presence.ts`, so a menu or dialog stays in the DOM for its close duration (150 ms) after it closes. The production CSS minifier rewrites `150ms` as `.15s`: read a CSS time with its unit (`toMs`), never a bare `parseFloat`, or the exit animation never plays. Timings are tuned to 250 ms (200 ms for an onboarding step) through the variables the skill exposes (the Notion card's budget). The wizard's steps use only the enter half of the skill's page side-by-side (`.t-step`, `StepSlide`, with `key={step}`): the skill's version keeps both pages in the DOM, ours mounts one step at a time.
**Rule:** New motion = another snippet in that file plus the hook; never commit the skill's folder or its CLI. The shake on a refused field (`.t-shake`, `lib/use-shake.ts`) is ours, not the library's: put its `ref` on a wrapper whose className never depends on state (React rewrites a changed className and drops the class mid-shake), and keep the field's red border on `:focus` too, since the field is focused when it shakes. A test that checks an element is gone after closing waits at least 250 ms (`tests/e2e/motion.js` shows how to measure it).

## Chart colours are fixed per sector, and our own script validates them
**Problem:** The Notion card says to run `validate_palette.js`, and a new chart colour looks like a free choice.
**Reality:** That script is in neither repo. `scripts/validate-palette.mjs` is ours: it reads the three `/* palette:… */` blocks of `app/globals.css` and checks, per theme, contrast on the card, distance between colours, distance under colour blindness, and the red/amber band kept for status. A sector's colour is its place in `SERIES_ORDER` (`lib/chart-series.ts`), i.e. `--series-N`, the same on every chart and in the "…" menu. The donut is a different thing: it sits on a black card (`bg-sidebar`) in every theme, with six pastels in rank order (`--slice-1` to `--slice-6`, biggest slice first) and a neutral `--slice-other`, the same values in all three blocks and checked against `--sidebar`, not `--card`. Its Critical / Warning slices (severity breakdown) take `--slice-critical` / `--slice-warning`, a separate validated pair; the family slices may be lime or pink because their meaning is in the legend.
**Rule:** A new sector goes at the end of `SERIES_ORDER` with its token in all three blocks; never reorder. After touching a colour run `node scripts/validate-palette.mjs` (`tests/e2e/palette.js` does it in the suite). Don't loosen its thresholds to make a colour pass. Text on the donut's card uses `text-sidebar-foreground`, never `text-muted-foreground` (dark grey on black in light mode). The ring is filled path segments with rounded corners built in `charts.tsx` (`segmentPath`); `tests/e2e/donut.js` guards its shape, gaps and contrast.

## The gauges and the stock chart read limits from an alert's params
**Problem:** A gauge "toward the limit" or a stock bar against its minimum looks like it can use limits the frontend knows.
**Reality:** It can't: pressure and temperature limits come from each uploaded row, fuel and oil from literals in the backend's `pipeline/alerts.py`. The backend puts them in the alert's params (`limit`, `limit_side` "max" / "min", `limit_unit`; `min_stock` next to `stock`), and `lib/chart-series.ts` (`gaugeReadings`, `stockRows`) reads them. Alerts saved before that have none, so on an account that has not uploaded since, both cards stay hidden and nothing is guessed. Each shows the last reading that raised an alert, not a live value.
**Rule:** Never draw a limit the alert did not carry. A new gauge is a backend `limit_kwargs(...)` on its alert; this side needs no change.

## A phone number is libphonenumber's call, on both sides
**Problem:** A phone input looks like a text field with a regex, and adding the library that does it right looks like a plain `pnpm add`.
**Reality:** `lib/phone.ts` (libphonenumber-js, `min` metadata) checks and writes E.164 and `components/sentria/phone-field.tsx` formats as you type; the backend's `pipeline/phone.py` checks again with the Python libphonenumber and has the last word (error code `phone_invalid`, a bilingual message). The field keeps digits only, so letters never stay in it; a number with no country code is read against the account's country (`sentria_country`) or refused. The pnpm in this sandbox (10.28) rewrites unrelated lines when it adds a package (it drops every `libc:` line from `pnpm-lock.yaml`); the lockfile change here was kept to the new package's own lines, which a frozen install accepts.
**Rule:** Never write a phone regex. A number the app texts goes through `checkPhone`. After a dependency change, diff `pnpm-lock.yaml` and keep only the new package's lines, then prove it with a clean `pnpm install --frozen-lockfile`.

## A quiet screen is only good news if the source answered and the data is recent (L4)
**Problem:** "0 critical" and an empty alert list read as healthy. Two things leave exactly that on screen: a department that stopped uploading three weeks ago, and a read that failed.
**Reality:** The API answers a failed list read with HTTP 200, an empty list and the error beside it (`/alerts` sends `{"alerts": [], "error_code": ...}`, `/recommendations` sends `{"recommendations": [], "error": ...}`; the Field team routes do the same). `lib/answer.ts` `readList()` tells an answer from a failure, and every reader of `/alerts` and `/recommendations` goes through it (`tests/e2e/notmeasured.js` reads the source to prove it). A failure shows `SourceNotice` (with a retry that asks again), a dash (`NotMeasuredFigure`) where a count would be, and none of the calm sentences ("No alerts in this period", "No data for ...", "No industry data", "No report to produce", "Everything here is under control"). Rows already held stay on screen with the notice, and the bell keeps its list and says it could not check. The Sites page has no data behind it yet (sites live in local state, and "Connect" only flips a flag), so a site with no assets reads "Not measured" (dashes, an empty health ring, no "running normally"). The age of the data comes from `GET /freshness` (migration 012): `lib/freshness.ts` `assessFreshness()` says stale when the newest stamp of the sector (of the department, on a department tab) is older than `stale_after_days` (sent by the API, 7). Stale: the dashboard warns (`FreshnessNote`), Tracking, the Calendar, the Report and the Profile show the same warning (`AccountFreshnessNote`), and every zero reads "—" / "Not measured"; non-zero figures stay, they happened. It claims nothing when it cannot know: no migration (`persisted: false`), no stamp yet for that sector or department, a failed `/freshness`.
**Rule:** Never read a list from the API with `Array.isArray(d) ? d : []`: use `readList`. Never decide "stale" from the date of the last alert (a clean upload leaves no alert; the Profile's freshness card reads the stamp and falls back to the last alert only when there is none). Never repeat the 7-day limit in the app. A new view that shows a count or an empty state as healthy goes through `readList` and `assessFreshness`, and a zero from either reads "not measured".

## The React Compiler lint blames a memo for a helper call elsewhere
**Problem:** In `calendar-view.tsx`, `const shown = (n: number) => known ? n : "—"` and `{shown(stats.deadlines)}` made `eslint` fail with "Existing memoization could not be preserved" on `useMemo(..., [visibleEvents])`, a hundred lines above and unrelated to the helper.
**Reality:** `stats.deadlines` is derived from `visibleEvents`. Passed to a function the compiler cannot see into, it is assumed to be mutated, which stretches `visibleEvents` past the memo. The error names the memo, not the call that caused it.
**Rule:** In a component that has such memos, decide with a plain boolean (`const deadlinesKnown = known && !(stale && stats.deadlines === 0)`) and render `{deadlinesKnown ? stats.deadlines : "—"}`. When this error appears with no obvious cause, revert hunks of your diff until it goes away; the line it points at is not the culprit.

## Third-party skills
**Reality:** `.claude/skills/transitions-*` and `skills-lock.json` are installed, uncommitted, and licensed "no redistribution".
**Rule:** Don't commit them without the owner's say-so.

## Two branches, Vercel deploys `main`
**Reality:** Work goes to `new_feat`, which is not merged into `main`.
**Rule:** Never push to `main`; no PR unless asked.

## Secrets are scanned at commit time
**Problem:** The frontend only holds public Supabase values, so a leaked key looks unlikely.
**Reality:** The backend repo once leaked a real `.env`. `scripts/check_secrets.py` (same file as the backend's) blocks `.env`/key files and secret-shaped values in a pre-commit hook and in GitHub Actions. Only `NEXT_PUBLIC_*` values belong in client code.
**Rule:** Enable the hook per clone (`git config core.hooksPath .githooks`). Mark deliberately fake lines `secret-scan: allow`; never weaken the patterns.

## Plan numbers come from the API
**Reality:** `lib/plans.ts` holds only default values; `applyEntitlements()` overwrites `ENTITLEMENTS`, `PLAN_LIMITS` (labels are generated from the numbers) and `DEPARTMENT_GROUPS` in place from `GET /plans` after sign-in (`lib/entitlements.ts`), then fires `PLAN_UPDATED_EVENT`. Views that read them at render must re-render on that event. The backend calls the retail sector `retail`, the app `commerce`.
**Rule:** Never write a plan number into a component or a string. Change it in the backend's `pipeline/entitlements.py`, and the bundled default here only to keep it in step.

## The pricing page's capability list is the API's, with no copy here
**Problem:** The pricing page lists what each plan can do, and a list in a component looks like the place to edit it.
**Reality:** `GET /plans` sends `tiers` and `capabilities` (backend `CAPABILITIES`: tier, lowest plan, live or soon, French and English label). `applyEntitlements()` stores them in `TIERS` / `CAPABILITIES` (lib/plans.ts), all or nothing, and `components/sentria/capability-matrix.tsx` draws them. There is deliberately no bundled copy: until the API has answered, or when it sends nothing usable, the section is simply not drawn. The plan cards' tracking, SMS and Intelligence rows come from flags the backend derives from the same list. Only some capabilities are enforced (see the backend's gotcha); the page lists what each plan includes, it does not itself block anything.
**Rule:** Change a capability's plan, label or live flag in the backend only. A suite that opens the pricing page must serve `/plans` (tests/e2e/plans-fixture.js is the backend's answer, kept by hand).
**The green "SentrIA Intelligence" banner above the matrix is the exception:** `ML_FEATURES` in `pricing-view.tsx` is written by hand on purpose, so it shows even when `/plans` is down or the backend has not been deployed yet. It repeats four rows of the matrix and carries the seasonal-advice disclaimer (stock advice, never medical advice), which the matrix no longer prints. It was dropped once by accident when the matrix replaced it and the founder asked for it back. Keep it; if a row there changes, change the backend's list too.

## Pickers list three countries, the table keeps them all
**Problem:** Trimming `COUNTRIES` to the launch markets breaks the currency, time zone and phone checks of every account that already chose another country.
**Reality:** `COUNTRIES` (`lib/locale.ts`) is the whole table that `countryFor`, `currencyFor`, `writeCountryCode` and `lib/phone.ts` read. What a picker offers is `pickableCountries(current)`: the codes in `LAUNCH_COUNTRY_CODES` (Benin, Côte d'Ivoire, Senegal, the markets the legal review covers) plus the country the account already has.
**Rule:** Open a market by adding its code to `LAUNCH_COUNTRY_CODES` after its legal check. Never delete a row from `COUNTRIES`. A new country picker calls `pickableCountries`. `tests/e2e/launchcountries.js` guards this.

## Removing a contractor opens a hand-over, and the SMS drafts are browser-only
**Problem:** The trash button on the Contractors page looks like a one-call delete, and the "Messages ready" texts look like a queue the server keeps.
**Reality:** The button opens `handover-dialog.tsx`. It reads `GET /contractors/{id}/handover` (open tasks and the API's ranking: same role, free, light load, no deadline clash) and confirms with `POST`, which moves the tasks one by one and removes the person last. Only a person with no open task takes the plain `DELETE`, which the API now refuses otherwise (`contractor_has_open_tasks`). A failed save can leave some tasks moved; the same request run again finishes, so the dialog keeps its choices. The drafted texts come back in the POST, are stored in this browser only (`sentria_sms_drafts`, `lib/sms-drafts.ts`, cleared at sign-out with the per-user keys) and listed by `SmsDraftsCard`. Nothing is sent: Send is off and says "SMS not yet active" until F-SMS2. The dialog takes the page's `tx` as a prop: a fresh `useTx()` starts in French for one render and the plan would be fetched twice.
**Rule:** Remove a person through the dialog, never `deactivateContractor` from a view. Ranking changes go in the backend's `pipeline/matcher.py`; the app only shows what it returns. Moving the drafts to the server is part of F-SMS2, and Send must go through the backend's `SmsGate`. `tests/e2e/cdelete.js` guards this.

## The dashboard's numbers wait for the first `/alerts` answer, and the bell rings on a diff
**Problem:** `alerts` starts as `[]`, so before the first fetch resolves every KPI reads 0, the pills say 0, the chart says "No alerts in this period" and the empty "no data" card shows. That reads as good news.
**Reality:** `dashboard-view.tsx` keeps `alertsLoaded` (true after the first answer, good or bad; a language switch does not reset it). Until then the three KPI layouts keep their tiles (the label is real, and the tag, number and line are `Skeleton` placeholders, `data-kpi-skeleton`), the chart and breakdown cards show `Skeleton`, the pill counts and the "N signals" badges are hidden, and the empty states (`hasNoDataForSector`, the industry "No industry data") wait for it. A failed load sets it too, so nothing pulses over the error banner. The priority tiles carry no number while the list is empty, which includes the time before the first answer. The bell (`app-shell.tsx`) rings when a critical alert whose task key was not in its last good read, and newer than the "seen" time, shows up: the first read only sets the baseline, a failed read sets nothing but the "could not check" line in the list (L4), and an upload fires `ALERTS_UPDATED_EVENT` (`lib/alerts-event.ts`) so the bell re-reads at once. The ring is `.t-bell-ring` (240 ms, ours, in `app/transitions.css`); the icon is remounted on each ring (`key`).
**Rule:** A new figure fed by `alerts` shows a placeholder, not a 0, until `alertsLoaded`. A new empty state for "no alerts" is gated on it. Anything that saves alerts calls `announceAlertsUpdated()`. `tests/e2e/vizpolish.js` guards this.

## The dashboard's entrance is ours, and the data motion waits for its block
**Problem:** The founder's reference video ("Dashboard Animations") has the page rise block by block, numbers count up and charts grow. The 250 ms budget (above) fits menus and dialogs, not a page arriving. The obvious versions break: a chart that starts when its data lands plays behind a card that has not risen yet; a block keyed on translated text replays on a language switch (the app asks for `/alerts` four times at start-up, `fr` then `en`, once it reads the stored language); an animation that keeps its end state leaves a transform on the block, which traps dropdowns and fixed layers.
**Reality:** `.t-enter` (the "ours" section of `app/transitions.css`) rises a block with fill mode `backwards` only; `enterAt(n)` in `lib/motion.ts` sets its place `--i` (0 to 9, 60 ms a step, 420 ms each, so the page has risen before one second). The data motion inside (`.t-grow-y`, `.t-draw`, `.t-sweep`, `.t-reveal-x`, `.t-pop` and the `CountNumber` counters) waits for its block through the Web Animations API: `waitForEntrance` (a ref callback on each animated mark) and `entranceWait` push its delay back by what is left of the enclosing `t-enter` delay, and data that arrives after the rise plays at once. A custom property set by the keyframes cannot do this: an animation's own value never reaches `animation-play-state`. `CountNumber` keeps the real text in the page, see-through while it counts, and draws a CSS counter on a registered integer over it, so reading, copying and tests see the final number; the same transition makes a changed value follow. A block replays only when it is a new element: KPI tiles are keyed by the French name (`k.id`), the ring's sweep by its parts' ids, the plot by its series keys and day count. Each layout `DashboardView` returns has its own root `key` (`overview`, `industry`, `logistics`): `filterSector` starts at `all`, so a sector's own page replaces the generic one a frame after it mounts, and without keys React hands the generic page's blocks to the new page. A reused block whose `--i` changes after it began to rise gets a new delay and starts a second time (a second `animationstart`; seen in about 1 run in 20 of `dashmotion.js` before the keys). On a busy machine a mark or a counter can start up to about 80 ms before its block: the block fades in on the compositor (opacity, transform), and its start time trails a main-thread animation (clip-path, a counter) created in the same commit. The delays are right, the two clocks start apart. The donut's total stays mounted under a hovered slice's number, because remounting it would count up again at every hover. The modal backdrop blurs the page behind it (`backdrop-filter`, in the modal snippet).
**Rule:** New animated data gets a `t-` animation with fill mode `backwards` (never `forwards` or `both`), `ref={waitForEntrance}` on the element, and a line in the `prefers-reduced-motion` block. Key an animated block on an id, never on translated text. A test of timing reads `animationstart` events like `tests/e2e/dashmotion.js`, not fixed sleeps. A new layout returned by `DashboardView` gets its own `key` on its root. The other pages rise the same way: the three columns of the Ask SentrIA layout at places 0, 0.4 and 0.8 (`ask-header.tsx` for Tracking and Field team, written out on Calendar, Sites, Ask, Report, Profile and Settings), then what sits below at 1.6 and after. Only fixed blocks carry `t-enter`; a list item, a card or a row that is made again by a filter, a search or a week change would rise at every keystroke. `tests/e2e/pagemotion.js` guards the pages and reads the CSS delay, not event times. `tests/e2e/dashmotion.js` allows 150 ms of that skew (`SKEW`); a mark that is not held back at all starts 180 ms or more early, so the check still catches it. Do not tighten it to fix one slow run.

## The sign-up email is a Supabase dashboard setting, and the repo holds its source
**Problem:** The confirmation email looks like app code and is not. Supabase sends it from its own template and its own shared sender, and no deploy changes either. The app can only influence it through the sign-up call.
**Reality:** `supabase/templates/confirmation.html` is pasted by hand into the dashboard (Authentication, Email Templates, Confirm signup); `supabase/templates/README.md` has the steps, including the custom SMTP sender, which is the founder's address and key and never goes in the repo. One file holds both languages: it reads `.Data.language`, which `auth-screen.tsx` sets on the sign-up call to `"en"` or `"fr"` (the interface language on screen when the button is pressed; any other language shows French, so the call says `"fr"`). A missing value renders French. The file never prints `full_name`, `company_name` or `username`, because whoever fills the form types those and can type someone else's address, so the mail would reach that person from our sender with text the sender did not write. Colours are literal hex, since email apps do not read CSS variables: they are the brand tokens in sRGB and `tests/e2e/signupemail.js` fails when a token moves. The reset-password email is a separate Supabase template and is still the default.
**Rule:** Change the email by editing the file, pasting it again in the dashboard, and running `tests/e2e/signupemail.js`, which renders it with Go's own `text/template` and `html/template` when Go is installed. The page is `noindex` with `referrer: no-referrer`, so the address never reaches another site. The boss makes the link from the task detail ("Copy field link", `FieldLinkButton`, `POST /assignments/field-link`); the page's language is the one the boss's app was in. It needs `FIELD_LINK_SECRET` on the API (Render); without it the button says field links are not switched on.
**Rule:** Keep the page's calls free of sign-in. Show the field person nothing the API does not return from `GET /field/{token}`.

## Field notes and photos on the page and in the task detail (F-CONTRACTOR)
**Problem:** A phone photo is several megabytes, and a stored photo must never be reachable without a sign-in.
**Reality:** The field page shrinks a photo to a JPEG of at most 1600 px on the phone (`shrinkPhoto`) before sending it as a file upload; the API re-encodes it again and caps each person at 5 notes and 3 photos. What the page sent in a visit is kept in the page, so the counts survive the switch to the "done" screen. The boss reads them in the task detail (`FieldReports`): notes as text, photos fetched signed in as blobs (an `<img src>` cannot carry the sign-in), nothing shown until something has arrived.
**Rule:** Fetch photos only through `fetchFieldPhoto` (signed in). Never put a photo's address where a signed-out person could load it.

## A cached read of server sentences must carry its language
**Problem:** After switching to English, an opened alert still showed its Recommendation and Why in French while its message was English.
**Reality:** The API writes those two sentences in the `lang` the request names (default French). The list read reloads when the language changes, but the one-alert read in `dashboard-view.tsx` was kept by alert name only, and a French answer still in flight could land after the switch.
**Rule:** A client-side copy of a server-written sentence stores the `lang` it was asked in, is used only while that matches the current language, and an in-flight guard is keyed by item and language. `tests/e2e/recolang.js` covers both the finished and the late read.

## Robo's tour points at `data-nav` and `data-tour`, and drops what is not on screen
**Problem:** The tour (`components/sentria/guide-buddy.tsx`) rings a menu item or a dashboard block and says what it is for. Renaming or moving one silently leaves a step pointing at nothing, and a new account has no cards, trend or breakdown at all.
**Reality:** Menu items carry `data-nav="<view>"`, dashboard blocks carry `data-tour="kpis|trend|breakdown|alerts|import"` (`dashboard-view.tsx`). A step whose target is not on screen is dropped; the data-dependent dashboard steps (`needsData`) collapse into one "what you will see after an import" step. The deeper chapter reads the account's own columns from `lib/csv-columns.ts`, so a new department there is explained without touching the tour.
**Rule:** Move a block and keep its `data-tour`. A new block worth explaining gets a step in `lib/guide-steps.ts` and an attribute. `tests/e2e/guide.js` walks both chapters with and without data.


## "What happened?" sits in a done task's detail, and its words follow the sector (F-OUTCOME)
**Problem:** The answers look like plain labels, and the count looks like something the app can work out from the board.
**Reality:** `OutcomeAsk` (`components/sentria/outcome-ask.tsx`) shows in the board's task detail only when the task is done and the plan is Pro or up (`useEffectivePlan`; below that nothing is asked and `/outcomes` is not called). It reads `GET /outcomes` and posts `{task_key, alert_key, outcome}`, plus `bucket` and `currency` for an avoided problem's optional cost range (the `cost_taps` ranges, `bucketRange`). The count per kind of problem ("3 real problems, 1 false alarm") is the API's tally, moved by hand after an answer so a changed answer is never counted twice. The words come from `lib/outcome-words.ts`: stock-out (health, commerce/retail), breakdown (industry, energy, transport), loss (agriculture), delay (logistics), problem otherwise. The API moves the confidence score from 3 answers, at most 10 points: a count, never called machine learning on screen.
**Rule:** A new sector gets a line in `BY_SECTOR`. Keep the request to those fields, the API refuses others. `tests/e2e/outcome.js` guards this.

## Search indexing needs the public address
**Problem:** The canonical link, the sitemap, robots.txt and the share card all need the site's own address. A wrong one tells Google the page lives somewhere else.
**Reality:** `lib/site.ts` reads `NEXT_PUBLIC_SITE_URL`, else Vercel's `VERCEL_PROJECT_PRODUCTION_URL`, else localhost. `/` is the sign-in screen drawn in the browser, so `app/page.tsx` also renders the pitch (both languages) in a `sr-only` block and the JSON-LD on the server.
**Rule:** Set `NEXT_PUBLIC_SITE_URL` on Vercel to the real domain. Keep the `sr-only` text equal to the visible sign-in text: it must never say more than the screen does.

## Suites fail on `next dev` that pass on `next start`
**Problem:** Run against `next dev`, about eight suites fail (`sheettabs`, `verify`, `weekrep`, `brand`, `cdelete`, `dashmotion` and others) and look like real bugs.
**Reality:** The dev server's "N" badge sits in the bottom-left corner and covers the departments menu button, and dev builds are slow enough to break the motion timings. On a production build they pass.
**Rule:** Judge a suite on `next build` + `next start`, as the build entry above says. A failure seen only on `next dev` is not a bug.

## The tour opens on a list of parts once it has been finished
**Problem:** The tour looks like one fixed run (hello, menu, "Go deeper"), so a test or change that expects "Take the tour" to always start at `hello` is wrong after the first finish.
**Reality:** `components/sentria/guide-buddy.tsx` reads `sentria_guide_done` when it opens. Unset: the whole tour from `hello`, as before. Set: a list of five parts (menu, dashboard, import, tracking, sites), each opening on its own, plus "Play all parts". `lib/guide-steps.ts` (`partSteps`) builds them: menu is the quick tour, dashboard and import are the two halves of the deeper chapter, tracking and sites are short chapters of their own. Finished parts are kept in `sentria_guide_parts` (this browser only, not in `ACCOUNT_KEYS`). A part opened from the list ends with Done and closes; a chain (Play all, or Go deeper) carries on and drops the goodbye cards until the last part.
**Rule:** A test that replays the tour sets `sentria_guide_done` and expects `data-step="parts"` (`tests/e2e/guideparts.js`). A new part is added to `PartId`, `partCards` and `partSteps`, with a card in both languages.

## A view must ask the API in the language it is shown in, from its first request
**Problem:** On an English account the recommendations (and the alerts) appeared in French, or flashed French, then changed to English. Sometimes the French stayed.
**Reality:** `useLocale()` keeps its own state per component and starts as French (the hydration render must match the server's). A view that mounted after the sign-in check read the saved language one tick later, so its first `/alerts` and `/recommendations` went out with `lang=fr`, then again with `lang=en`. Two answers raced, and the dashboard's recommendation read, the report and the profile page had no guard, so the French one could land last. `markLocaleHydrated()` (called by `AuthGate` once the first page has hydrated) lets everything mounted afterwards read the saved language in its first render. `useLatestRead(key)` (`lib/latest-read.ts`) drops an answer that arrives after a newer read started or after the language or site changed.
**Rule:** A read of server-written text takes its language in its first render and runs under `useLatestRead(`${lang}|${site}`)`, or under an effect with a `cancelled` flag. `tests/e2e/langload.js` fails on any `lang=fr` request from an English account and on a slow French answer after a switch.
